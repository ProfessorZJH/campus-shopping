# 03 · 意图、记忆与上下文保真契约

## 1. 设计目标

解决“记得聊过订单但丢了订单号”“只保留退款关键词却丢了否定条件”“从 A 店切换到个人购物却带入 A 店内部结果”。不承诺大模型永远理解正确，不以扩大上下文窗口代替可追溯记忆。

采用：原始消息 + 精确实体引用 + 带来源约束 + 范围内摘要 + 按需原文回溯 + 后续受控长期偏好。没有常驻 Task 实体，但存在能够跨轮检索的证据关系。

## 2. 必须区分的资料

| 类型 | 例子 | 写入者/可信程度 | 使用规则 |
|---|---|---|---|
| 用户原话 | “订单 CS001 不要取消，先查资格” | 用户输入，真实原话但不是授权系统指令 | 保留来源，不能自动判为业务事实 |
| 实体线索 | CS001、SKU、店名 | 确定性解析优先；模型补充候选 | 未验证只用于受控查询，不直接执行变更 |
| 已核实实体关系 | orderId 属于该买家/该店 | Java 查询验证 | 访问时仍重新鉴权；验证状态不是永久授权 |
| 约束和条件 | 预算 30 元；不含糖；只查不改 | 模型解析候选 + 原文锚点 | 按需求锚点更新当前值和来源，不能猜测缺失参数 |
| 业务观测 | 10:00 库存 8 | Java 工具结果 | 带 observedAt/版本，执行时重新查询 |
| 执行回执 | action A 已加购两瓶 | Java 事务和动作账本 | 是执行真相，不从助手文字提取“成功” |
| 长期偏好 | 以后饮料优先无糖 | 用户明确允许持久化 | 新请求优先、可查看/改/删；不代表健康诊断 |
| 摘要 | 用户先咨询换货，不行再看退款 | 派生文本，有损 | 引导检索，不能单独证明授权或业务状态 |

## 3. 实体与来源模型（目标逻辑结构）

```json
{
  "refId": "ref_order_17",
  "entityType": "ORDER",
  "literal": "CS001",
  "resolvedId": "order_internal_17",
  "sourceMessageIds": ["msg_17"],
  "verification": "VERIFIED_AT_OBSERVATION",
  "verifiedAt": "2026-11-06T02:00:00Z",
  "scopeLabels": ["SELF_ORDER:user_1"],
  "lastMentionSeq": 17
}
```

时间和 ID 均为示例。首期用 `sourceMessageIds` 定位原文；只有逐字高亮等实际功能需要时再增加 `sourceSpan` 并统一字符索引规则。`scopeLabels` 由 Java 依据实际资源和使用目的维护，不由模型自证。

同一订单可能同时是本人购买的订单和本人经营店铺的销售订单。不要将实体永久分类成唯一 CONSUMER/MERCHANT；允许同一对象在不同已授权视角产生不同字段投影。消费者不能因为内部 ID 相同就得到商户内部备注。

## 4. 约束继承不能只有实体记忆

只记订单号不能保留“不要退款”“只有缺货才换牌子”。M2 每条当前约束保留 key、类型化值、需求锚点（实体/展示集合或起始消息）、来源消息及范围即可。长期偏好在后续阶段单独管理；字符跨度与完整约束版本链不作为 M2 的完成条件。

```json
{
  "key": "budgetCent",
  "value": 3000,
  "appliesTo": {"displaySetId": "display_9"},
  "sourceMessageId": "msg_18",
  "scopeLabels": ["USER_PRIVATE:user_1", "PURPOSE:SHOPPING"]
}
```

`appliesTo` 不应只有 domain=CONSUMER，否则选牛奶的 30 元会污染另一个手机选购目标。初次尚无实体时可引用发起需求的消息 ID；后续明确继承该消息的约束，而不是依赖一个可变全局预算。

这套关系记录不是 Task 状态机：没有任务调度、计划依赖、跨天恢复或通用完成状态。它只是为语义继承提供证据，仍然需要每轮决定哪些相关。

用户纠正时更新相同需求锚点下的当前值与来源，旧约束移出当前上下文，变化过程通过保留的原始消息回溯。用户说“不是 A，是 B”，先移除旧候选，验证 B；不把两个值同时放入提示词让模型自行选。

## 5. “第二款”与列表快照

每个推荐/订单列表保存有界 `displaySetId`，其中每项包含 ordinal、稳定资源 ref、显示版本/时间及来源 Run。用户点击卡片时可发送该引用；用户口头说“第二款”时再用原话和最近展示集合匹配。

不能通过刷新商品目录的排序重新计算“第二款”。展示集合里保留的价格只是原报价，不是执行时的价格承诺。重试用旧卡片时 Java 重查可售性和用户约束；重大变价或违反原条件时提示，不擅自换 SKU。

## 6. 安全的上下文构建流程

1. Java 验证 Conversation 所有者、当前账号状态，读取本轮原始消息/合法回复引用。
2. 获取当前可用权限上限；初步检索仅访问当前用户可见、可向指定模型外发的最小元数据。不能认为“元数据”天然不敏感，店名、订单号和文档标题也可能受限。
3. 提出业务视角与目标候选：规则只处理可靠结构化线索，复杂语义由受限模型或澄清处理。
4. Java 验证候选对象及范围，形成执行片段；明确用户请求优先，页面只是低优先级线索。
5. 在已验证范围内取得实体引用、当前相关约束、最近原文、摘要与少量历史证据。每个内容块带可追溯来源。
6. 按 Token 预算装配，不在截断时拆散 tool_call 与其 tool_result；旧模型中间过程没有必要全部重放。跨轮可以采用精简事实，但本轮 SDK 内部工具配对必须完整。
7. 输出前重新校验敏感证据访问资格和外发政策。变价、库存、订单状态用工具刷新，不靠记忆回答“现在”。

商户 A/B 汇总只在明确的本轮请求内形成受控联合范围，分别授权取数、使用最少聚合字段。不是允许所有未来 Run 继承 A/B 全部历史。

## 7. 压缩、回溯与上下文优先级

摘要只覆盖确定消息边界，如 `coveredSeq=1..40`，记录 summaryVersion、sourceMessageIds/来源段、范围标签和模型版本。优先从原文增量生成，避免无限“摘要再摘要”累积漂移。

压缩前保留精确实体、金额、数量、排除项、条件、未解决问题和真实动作回执。数字和 ID 可做确定性保真检查；否定/条件的语义保真必须靠专门评测、原文锚点和必要时回溯，不能宣称已经实现完全无损。

触发回溯的情况：本轮纠正“我之前说的是…”；摘要与结构化约束冲突；多个“那笔”候选；明显缺少前置条件；旧事实无法追溯。回溯后仍不唯一则澄清。

常见冲突：

| 冲突 | 裁决 |
|---|---|
| 旧预算 30，本轮明确改 50 | 在相同需求锚点下生效新预算 |
| 长期无糖偏好，本轮明确要普通可乐 | 本次明确要求优先，不静默删除长期偏好 |
| 摘要“申请退款”，原文“先别退” | 回溯修复摘要；不允许写操作 |
| 旧工具结果库存 8，当前查询库存 0 | 使用当前值，保留历史仅作解释 |
| 旧 Action 成功，模型新总结说失败 | 以 Java 动作账本为准 |

系统策略与权限不参与“谁更新就听谁”的排序。历史原话即便被结构化保存，也只是数据，不能升级为系统指令。

## 8. 多身份连续性，而非常驻身份

“看 A 店待备货订单” → “我昨天买的牛奶” → “A 店刚才那笔”：通过本轮视角、实体来源与显示卡片找回相关历史。`lastMentionSeq` 可帮助排序，不代表最新的一定是正确的。

两个浏览器标签页共享账号时，不以登录 Session 保存一个全局活动店铺覆盖双方。显式 `replyToMessageId` 优于全局最近事件；同一 Conversation 的 Run 采用有界串行与版本保护，跨 Conversation 不共享私有焦点。

“那笔能退吗”没有唯一对象时，任何架构都不能靠隐式状态保证正确；清楚询问业务对象比偷偷选择更合理。

## 9. 长期记忆和生命周期

第一阶段做实体、约束和原文回溯；后续做明确用户授权的长期偏好。记忆归属至少包含 owner + 业务用途；商户私有内容还包含具体商户/资源范围。店员私人记忆不能自动成为全店制度，制度应进入受控知识库或业务配置。

保留原文是指不因生成摘要立即销毁，不是永久保存所有内容。产品须提供会话/记忆删除、保留期限及授权撤销后的屏蔽策略。删除必须覆盖派生摘要、实体映射、缓存和后续索引；必要审计保留与对话记忆分开治理，不能将“合规审计保留”当作再次向模型召回的理由。

撤权后历史展示、SSE 输出和重连快照也需过滤；后续若启用事件回放，同样校验当前可见性。已被用户看到或客户端缓存的数据无法保证从现实世界撤回，但后端不得继续提供新的副本。

## 10. 旧数据兼容与隐私限制

不要把所有旧导购消息批量标记为公开、或认为“前端是消费者页面”就不存在内部知识结果。旧内容缺少细粒度来源时标为待验证的 legacy 范围，沿用已有知识指纹校验；无法可靠证明可见性时不送入新 Agent 的外部模型上下文，可显示受限提示或让用户重新查询。

用户手工重新输入其他商户数据与系统自动带入历史是不同风险：系统能控制自己检索和外发的数据来源，不能声称完全识别用户所有手工粘贴内容的真实来源。依然需要最小化外发和敏感内容过滤。

## 11. 最小实现边界

逻辑资料可先保存在一个版本化 `ai_context_state` JSON 及原消息元数据中，不为每种记忆类型新建微服务。实体/历史量大后再拆检索索引；长期偏好需要跨会话查询时单独建表。JSON 必须限量、可重建、按 scope 分组，不能成为不断增长的全量聊天副本。

SDK 只使用本轮 Java 提供的历史输入，不同时开启另一套未映射的持久化 Session。必要的 SDK tool messages 在当前片段内保存，跨范围不整体重放。[S3]
