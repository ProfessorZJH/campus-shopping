# 01 · 可用方案与选型决策

本文件区分“技术上可行”与“适合本项目”。没有经过同一评测集比较，不宣称某方案具有更高准确率或更低时延。以下推荐基于当前业务边界、已有 Java/Python 架构、开发维护成本及用户明确偏好。

## 1. 目标与选择标准

目标是让消费者自然完成导购、本人查单和明确加购，让商户自然查询自己获授权的经营数据。首期不做自动经营、多天自主任务或真实资金操作。

选择顺序：业务与权限正确性 → 用户操作连续性 → 复用已有代码 → 可观察及故障恢复 → 开发维护成本。不能为了省一张表删掉动作幂等记录，也不能为了“架构成熟”引入暂时用不到的工作流平台。

## 2. 三种整体架构均可行，但不要混着上

| 方案 | 核心 | 适用条件 | 代价 | 当前结论 |
|---|---|---|---|---|
| A：持续 Task/Workflow | Conversation 下维护长期 Task，任务有完整生命周期、依赖、检查点 | 跨天经营流程、长任务、复杂审批/补偿 | 任务归属、恢复与并发状态维护复杂；仍然需要指代消歧 | 保留演进方向，v1 不采用 |
| B：每轮范围解析 + 证据记忆 | 每轮形成受限执行范围；跨轮依靠消息、实体、约束和已执行动作 | 短查询、导购、加购、多身份自然切换 | 需要可靠的引用和历史召回；不能只用一段摘要 | **推荐** |
| C：隐式子会话 | 前端统一，后台按消费者/商户拆多个线程 | 业务域稳定、跨域请求很少 | 路由仍会出错；跨域引用和用户纠正较难追踪 | 可行，但当前收益不如 B |

推荐 B 不代表“无状态 Agent”。B 必须保存 Run 和写动作结果，也必须保留跨轮的否定、预算、条件及展示卡片顺序；删除这些状态会使 B 不可用。

## 3. 各模块可用方案与唯一推荐项

| 决策编号 | 主题 | 可用方案 | 本轮推荐 | 为什么/何时换方案 |
|---|---|---|---|---|
| D01 | 交互入口 | 单一对话；前后台分别嵌入同一助手 | 同一助手体验，可在多个页面唤起，不要求选择 Agent/工作空间 | “统一”不限制按钮位置，也不强制用户迁移页面 |
| D02 | 内部 Agent 组织 | 一个巨大 Agent；按域两组配置；多 Agent 协作网 | Consumer/Merchant 两组能力配置，共用 Runtime | 首期不做自主 Handoff，不为每个工具建 Agent |
| D03 | 运行时 | 原生模型 SDK + 自写循环；Agents SDK；LangChain；LangGraph | **OpenAI Agents SDK，先通过兼容性 POC** | 集中使用运行循环、工具、Trace；若关键提供商适配失败再比较替代，不同时运行两套 |
| D04 | 意图路由 | 全规则；独立分类 LLM；每轮混合解析 | 明确实体/交互引用短路 + 必要时模型语义解析 | 不为每轮强制多一次分类；不以关键词规则包办否定/条件理解 |
| D05 | 身份范围 | 全局 active_role；Task 范围；每轮 Scoped Run | 每轮 Java 验证范围；跨域请求拆有限执行片段 | 范围是执行约束，不是用户权限来源 |
| D06 | 工具选择 | 全量 Schema；按固定数切片；权限和相关性动态过滤 | 当前权限上限 ∩ 本轮业务范围 ∩ 已上线工具 ∩ 风险阶段 | 不固定 3～5 个；缺能力时受控重解析/澄清 |
| D07 | 近期上下文 | 固定轮数；完整历史；Token 预算与证据选择 | 原文窗口 + 精确引用 + 相关约束，按 Token 预算装配 | 不承诺保留 N 条必然正确，工具结果与工具调用须配对 |
| D08 | 关键事实 | 仅摘要；实体槽位；知识图谱 | MySQL 中带来源的实体、约束和卡片引用 | 不上 Neo4j；ID 精确保留，语义提取仍需校验 |
| D09 | 历史压缩 | 滚动摘要；范围内摘要 + 原文索引 | 分范围摘要、覆盖消息边界、按需原文回溯 | 不把压缩视为无损，不让模型摘要覆盖真实动作结果 |
| D10 | 长期偏好 | 自动画像；明确保存的偏好；全量向量记忆 | 后续加入明确允许保存、可查看删改的偏好 | 单次预算、订单状态不写成永久偏好；量大语义需求出现再考虑向量 |
| D11 | 用户认证 | 现有 Session；迁移 JWT | 复用 Session + Cookie + CSRF | Agent 不是引入第二套登录体系的理由 |
| D12 | 服务间调用 | 转发用户 Cookie；自报 userId；内部服务认证 + Run 能力凭据 | 独立服务身份 + 短效受限执行凭据，Java 绑定 actor | runId 只是标识，不是凭证；模型不得看到凭据 |
| D13 | 权限执行 | 自制 AOP；标准方法安全；现有显式 Case/Domain 校验 | 复用当前权限服务、资源归属和业务规则 | AOP 可减少重复，但不能代替对象级授权和事务校验 |
| D14 | 写操作 | 全自动；全确认；按风险分级 | 明确低风险直接执行，高风险 prepare → 确认 → execute | 查询退款资格≠申请退款；推荐≠授权加购 |
| D15 | 幂等 | toolCallId；请求内容哈希；服务端稳定 actionId | 入站消息去重 + 服务端动作账本 + 业务事务 | 相同参数不一定是重试；“再加两瓶”是新动作 |
| D16 | 持久化 | Redis 统一存；MySQL 统一存；二者分工 | MySQL 保存消息/派生状态/Run/动作；复用 Redis 做既有 Session/限流 | Redis 焦点缓存不是鉴权依据；不新增权威 ActiveScope |
| D17 | SDK 会话 | SDK Session；应用管理历史；服务端 Responses 会话 | Java 构建有界历史，SDK 不另持久化同一份业务历史 | 正式需要检查点时再做映射，不混用三套续接机制 |
| D18 | RAG | 重写检索链；全部 Agent 化；复用查询能力 | 封装现有商品召回与知识检索，权限仍在 Java | Milvus 用于已设计的商品语义索引，不宣称所有知识库都迁移到 Milvus |
| D19 | 用户流式体验 | 同步 JSON；POST token 流；Run + SSE | 保留旧 JSON，新能力采用建 Run、SSE 事件、状态查询 | 先输出进度/真实卡片；业务结论核验后发布，不伪造 token 流 |
| D20 | Trace | 默认云端全量；脱敏元数据；自建平台 | SDK 采集必要元数据，显式配置受控导出 | 生产先关闭默认外发；Trace 不等于交易审计账本 |
| D21 | 多意图/多店 | 同一模型混装；逐段执行；通用调度器 | 同一 Run 内有限顺序执行、各段独立范围 | 最终可按需合并授权结果，但不横向灌入所有原始私有数据 |
| D22 | 失败恢复 | 整轮重跑；从动作账本确定结果；Durable Workflow | 读取已提交动作结果，再决定安全重试 | 首期不自动重放长流程；跨天流程需要新 ADR |
| D23 | 发布与评测 | Prompt 验收；离线评测；全链路分层门禁 | 确定性安全测试 + 真实模型评测 + 故障注入 + 灰度 | 安全缺陷不能被总体平均分抵消 |

## 4. Runtime 的具体取舍

### 4.1 推荐：OpenAI Agents SDK

官方文档提供工具条件启用、运行上下文、手动历史管理和追踪等能力；非 OpenAI 模型可通过兼容客户端或模型适配接入。但“普通聊天成功”不等于 tool_calls、流式参数、JSON Schema 和 usage 全部兼容。必须验证本项目实际使用的服务端点和模型，而不是只看提供商名称。[S1][S2][S3][S4]

项目应在 `Agent.model` 或 Run 的模型配置上显式绑定客户端，避免并发请求改写全局默认模型。生产锁定 POC 通过的版本，不把浮动 latest 写进冻结基线。

### 4.2 可用备选：LangChain

LangChain 的标准 Agent 循环建立在 LangGraph 上，可使用其中间件、模型适配和观测能力；不能再以“LangChain 没 Trace”作为否决理由。[S5] 当现有关键模型在其原生集成中兼容性明显更好，且实测总维护成本更低时，才选择它。不能只为省几个工具定义同时叠加 LangChain 和 Agents SDK。

### 4.3 按需演进：LangGraph

LangGraph 面向显式状态图、持久化和恢复，不要求必须使用 LangChain。[S6] 如果正式需求包含跨天流程、复杂中断和多步骤恢复，评估它会更有意义。它的检查点仍不能取代 Java 的事务幂等与权限。

### 4.4 原生模型 SDK + 自写循环

对工具极少的简单助手可行。缺点是要自己处理工具轮次、错误、usage、Trace、终止条件和兼容性。它不是绝对错误的方案，也不是本项目当前首选。

## 5. 明确不采用的混合方案

不要同时建设全局 ActiveScope、常驻 Task 状态机、SDK Session 数据库和 MySQL 业务会话四套记忆；不要把卡片确认、风险审批、自然语言澄清设计为同一个“确认”按钮；不要把两个 Agent 的全部记忆装进一轮模型，再指望最终答案过滤解决泄露。

## 6. 可证伪的改选条件

以下证据才应触发架构调整：真实模型工具协议不兼容；每轮范围解析在冻结集上持续误关联；跨轮长流程已成为主要业务；持续性能测量发现现有存储/编排成为瓶颈。外部模型给出更复杂的架构图、未经校准的置信度数值，不构成改选依据。
