# 02 · 推荐冻结基线：Conversation + Evidence Memory + Scoped Run

版本：v1.1 整合推荐稿；日期：2026-11-06。目标是可商业化演进的校园导购与经营助手，而非演示型自动聊天，也非通用自主工作流平台。

## 1. 唯一推荐组合

**统一 AI 交互 + Consumer/Merchant 两组内部能力 + 每轮混合意图/范围解析 + 带来源的实体和约束记忆 + 有界执行 Run + Java Tool Gateway/现有业务系统。**

首选验证 OpenAI Agents SDK，保留 Java Spring Boot、Session/CSRF、已有 RBAC 与 DDD 边界、MySQL、现有 Redis 基础设施、既有 RAG 和 Milvus 商品语义召回。不在第一阶段引入独立 Task 生命周期、角色切换器、Memory Agent、向量用户记忆库或工作流集群。

这不是无状态方案：会话消息、用户约束、实体关系、Run 状态和动作结果都必须保存。所省略的只是为了判断“买家/商家”而建立的常驻任务实体、任务调度和全局角色状态机。

## 2. 业务范围与不做什么

消费者 v1：商品查询与推荐、商品规格/报价/可售状态、本人订单及售后查询、已授权知识问答、明确授权的低风险加购。购物车加购不等同于下单、支付或库存预占。

商户 v1：在当前有效具体权限下查询本商户订单待办、商品、库存、知识；需要统计指标时必须已有可信口径与查询实现。无实现的报表不允许模型编造。商户经营写操作作为后续阶段，优先做明确的预览与确认，不直接开放自主执行。

不纳入首期：真实支付/提现/清分、物流跟踪、优惠券、跨商户合并结算、平台管理 Agent、未经项目需求确认的余额/校园 schoolId、多天自主经营、自动授予权限。不能因为外部方案列出了这些工具就扩大业务范围。[R3]

## 3. 名词与职责

| 名词 | 语义 | 不能被误认为 |
|---|---|---|
| User/Actor | 登录主体，来自 Java 认证 | 用户自报的 role、模型参数 userId |
| Conversation | 用户可见对话容器及原始消息归档 | 固定买家/卖家身份 |
| Turn | 一条用户消息或一次明确 UI 交互 | 独立长期任务 |
| Run | 受理一个 Turn 的有限执行过程 | SDK Session、数据库事务或工作流平台 |
| Run segment | 本轮某个业务域/商户的受限执行片段 | 需要跨轮管理生命周期的 Task |
| Evidence Memory | 带来源、范围和时间的实体/约束/历史引用 | 永久真实的库存、价格和权限 |
| Action | 唯一、可审计的具体业务变更尝试 | 每个模型随机生成的 toolCallId |
| Scope | 本次可查询/执行的目标与限制 | 授权凭据或永久权限 |

跨轮保存的是消息和证据，不是恢复 Task。一个展示卡片列表可以用 `displaySetId` 保持“第二款”的顺序；它没有任务的计划、依赖、重试调度和完成状态，不只是把 Task 改名。

## 4. 核心不变量

1. 不要求用户选择工作空间、Agent 或买卖身份；相关页面可以唤起同一个助手。
2. 明确本轮目标优先于页面线索、旧约束和长期偏好；但任何用户文字都不能覆盖权限或业务规则。
3. 一个用户可同时有买家和多个商户成员身份；工具执行按本轮目标和当前权限逐次校验，不使用全局 active_role。
4. 模型只提出意图、实体候选和工具参数；Java 验证 actor、范围、具体权限、对象归属及当前状态。
5. 高风险 execute 不作为可由普通模型自由调用的工具；明确低风险加购允许直接执行，不重复询问“确认加购吗”。
6. 推荐、查询资格、讨论方案均不等同于执行授权；“如果不行再看看能否退款”不得变成退款命令。
7. 结构化实体 ID 精确保留原值和来源；语义事实提取仍可能出错，必须能回溯与纠正。
8. 订单/库存/价格/售后/权限的当前值以 Java 查询或事务结果为准，历史观测值需带 observedAt，不能冒充实时值。
9. Context Builder 和用户历史接口都需重查当前可见性；不只在工具层阻止新查询。
10. 已提交业务动作不因模型回答失败、SSE 断线或取消而消失；执行回执与生成回答是两类独立结果。

## 5. 架构与依赖边界

```text
统一 AI 交互（商城页面、个人页或商户页面可唤起）
  -> Java：Session 身份、会话归属、Turn 去重、Run 建立与准入
  -> Scope Resolver：安全元数据 + 当前请求，提出本轮意图/实体候选
  -> Java：验证资源及当前权限，形成不可随意扩大的执行片段
  -> Context Builder：取该范围的原文、实体、约束、摘要与偏好
  -> Python FastAPI + Agents SDK：运行 Consumer 或 Merchant 配置
  -> Java Tool Gateway：服务身份、Run 委托、参数、权限、对象/业务校验
  -> 原有 Case / Domain / MySQL；既有商品与知识检索能力
  -> Java：实际动作回执、授权结果卡片、运行状态、SSE/结果查询
```

Java 现有模块继续拥有业务事实。SDK 类型、HTTP DTO 和模型客户端不要进入领域模型。Python 模型请求不直接读取交易 MySQL；Java 等待外部模型期间不保持业务事务/行锁。Tool Gateway 可在现有 Java 应用内实现，不是新增微服务。

共享 Runtime 不意味着共享每个请求的可变上下文。每个 Run/片段使用独立 context，模型客户端按实例或 Run 配置；不能修改全局 actor、全局默认 merchantId 或共享消息列表。

## 6. 意图与范围解析：怎样既自然又不盲猜

### 6.1 三步处理，避免先泄露后过滤

第一步，Java 取得当前主体允许的能力上限。没有商户权限的用户不暴露商户内部工具；公开商家商品查询仍然属于消费者能力。

第二步，用当前原话、用户明确点击的 `replyToMessageId/cardRef`、已授权的最小实体索引、明确的范围内继承关系解析请求。先确定“本人订单/店内订单/公开商品”等业务视角，再验证对象；不能先把所有店铺私有历史送给模型帮助选择身份。

第三步，Java 复核候选，装配本轮 scope 和工具集。非歧义问题不强制第二次分类模型调用；确实无法确定语义时允许一次有预算的受限解析或自然语言澄清。不能声称完全不需要模型路由成本。

### 6.2 优先关系

当前明确指令及明确 UI 回复引用 → 已验证的实体与相邻原文 → 与本问题相关的带来源约束 → 页面线索/最近交互 → 相关长期偏好。该顺序是检索和冲突处理原则，不是将历史用户内容升级为系统指令。

“用户只有一家店”只证明商户候选唯一，不证明“我的订单”一定指卖家订单。商户身份和资源归属仍要与本次目的分开判断。

### 6.3 歧义策略

有限候选：用简短说明和快捷选项。预算、用途、数量等开放问题：自然语言追问。用户能用语音或文字回答，不必总点按钮。普通澄清回复沿用消息入口，通过回复消息/选项引用创建下一轮 Run，不另建澄清生命周期。

对于“我的待处理订单”这类买卖双义请求，缺少可靠线索时优先澄清，不默认把所有有权限的订单都查一遍。只有用户明确要求比较/汇总，或低敏感的分组概览确实符合当前意图且成本受控，才分范围查询。

不采用模型自报 confidence>0.8 或置信度差<0.15 作为授权门槛；有真实校准数据前不冻结这些阈值。

## 7. 不用 Task 如何保持多轮连续性

例子：推荐牛奶 → 30 元内 → 不要含糖 → 第二款还有货吗 → 加两瓶。

系统保存推荐卡片顺序及 SKU 引用，约束记录绑定相关消息/展示集合。下一轮仅检索当前相关证据；用户转去问订单时，牛奶预算不会继承到订单问题。再次说“刚才第二款牛奶”可通过 `displaySetId + ordinal` 恢复商品，不需要恢复某个 Task。

对于“不用了”“换个品牌”“预算改成 50”，更新相同需求锚点下的当前约束及来源，使旧约束不再参与本次推理；保留原始消息以供回溯，不要求建立完整约束版本链。否定和条件不采用单个全局布尔值无限继承。细节见 `03`。

## 8. 多意图和多商户

一条消息含“查 A 店待备货订单，顺便给我买牛奶”：同一用户 Run 下顺序形成商户 A 和消费者两个执行片段，各自只接收必要上下文；动作有各自稳定 actionId。首期无需多 Agent 自主协商或通用 DAG。

跨店比较由明确请求触发，分别授权取数；聚合层只使用必要、可公开给当前用户的字段。可在同一结果中展示 A/B 店对比，这不是隔离违规；违规的是未授权取数或把 A 店私有历史无关地灌入 B 店工具调用上下文。

片段间不默认全局事务。一个查询成功、另一个失败，返回部分结果；不能说“全部完成”。跨范围原子写不在 v1 支持范围。

## 9. 两个完整交互示例

### 9.1 明确加购，免二次确认

用户：把刚才第二款 500ml 无糖饮料加两瓶。

恢复原展示集合 → 唯一 SKU/数量 → 读取本轮用户原话及排除条件 → Java 验证可售/累计购物车数量/当前价格约束 → 同事务写动作回执和购物车 → 返回 `SUCCEEDED` 的真实 actionId → 显示加购成功。

若用户只说“推荐两瓶”，不创建加购动作。若本轮中断后客户端重试，复用 Turn/Action，而不是再次增量加购。

### 9.2 跨身份无感追问

用户：A 店还有多少待备货订单？
系统：授权商户 A 查询，返回订单卡片。
用户：我自己昨天买的牛奶呢？
系统：明确切换到本人订单工具，商户 A 历史不进入消费者私有查询参数。
用户：刚才 A 店那笔能处理了吗？
系统：通过卡片和原文定位；多笔仍有歧义就展示候选。任何状态重新查询，不沿用上轮判断。

## 10. 冻结层级与变更限制

本文件冻结产品边界、执行责任和状态语义；数据库字段类型、模型选择、预算数值须在 POC/实施中验证。不能把“暂不引入 Task”解释为删掉 Run/Action，也不能通过加 `scopeToken` 宣称解决了自然语言误解。

更换 SDK 不应改变业务契约。只有出现明确跨天任务、复杂恢复或持续的路由失败证据时，才重评 Task/Workflow。此前“两个不同入口强制切换工作空间”“全局 active_role”“会话固定 agentType”“每句话一个 Task”“所有写入二次确认”的方案不作为推荐基线。

具体契约见 `03`—`06`；现状与来源见 `07`。
