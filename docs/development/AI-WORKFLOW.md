# AI 协作开发流程

适用于本仓库的人工与 AI 协作。沿用现有 PRD、SDD、ADR、接口和验收脚本，按风险选择验证范围；不要求每次修改都创建一套设计文档。

## 1. 需求任务

开始前写清四件事，可直接放在 PR 描述或相关规格中：业务目标、影响范围、关键不变量、可观察的验收标准。先核对分支/工作区及相关源码、调用方、测试和契约，确认是否已有可复用能力。

| 修改 | 最小设计记录 |
|---|---|
| 文案、样式、局部展示修复 | PR说明目标、范围及页面验收；不强制新增SDD |
| 普通业务缺陷 | PR写明触发条件、正确行为和回归场景；引用已有规格 |
| 跨域用例、API/数据库/权限或基础设施语义变化 | 更新相关SDD/契约；有新的架构取舍时追加ADR，写明兼容、迁移和失败处理 |

风险依据实际行为变化判断。订单页面改文案不自动等同于交易规则变更；UI改动若影响价格提交、权限或订单操作，则按对应业务风险验证。

## 2. 设计与契约

读取 [工程入口](../../AGENTS.md)、[文档索引](../README.md)及任务相关已接受规格/ADR。历史阶段报告记录当时的实现和环境，不作为新任务的自动授权或当前状态证明。

追踪从页面/请求到 Controller → Case → 领域能力 → Repository/远程 Port 的完整链路，列出输入输出、鉴权、状态变化、事务边界、锁顺序、幂等和故障语义。业务需求与源码不一致时记录差异，不能把当前实现直接当作正确答案。对实质业务选择无法从授权与资料判断时再澄清。

复用现有小傅哥 DDD 约定和 [Java规范](JAVA-STYLE.md)。避免新增无独立职责的接口/模式。HTTP与生成契约同步；数据库使用不可变版本迁移，说明新库、旧库升级和回退边界。

## 3. AI 实现

在基于最新 main 的 `codex/` 功能分支工作；先检查未提交改动并保留他人工作。按功能链路实现，保持业务规则在既有归属位置，避免夹带无关重构。

新库/临时服务作为默认验证环境，不读取或清理既有业务数据。Redis 默认不连接已存在的业务实例；仅在确认是测试专用的本机实例且显式配置 `REDIS_TEST_ADDRESS` 后复用，并使用随机命名空间，禁止全库清理。没有隔离 Redis 时不能把依赖它的测试记为通过。`verify-mysql-isolated.py` 默认禁用 Redis，只有提供上述测试地址才启用；CI 使用独立启动的 Redis。不把凭据、提示词或下游异常正文写入提交和日志。已有服务替换、真实模型调用、迁移或部署按本次明确授权执行。

## 4. 测试与审查

先运行与修改直接相关的回归，再执行所需门禁；失败先定位、修复并保留原始结果。测试应证明业务行为和边界，不为通过而删除断言、取消鉴权或改用未经说明的替身。

| 风险/范围 | 要验证的行为与现有入口 |
|---|---|
| Java、领域或跨域规则 | 相关JUnit和`mvnw clean verify`；`scripts/verify-release.py`、`verify-domain.py`、`verify-java-readability.py` |
| 订单、模拟支付、库存、退款、提案确认 | 真实MySQL事务提交/回滚、并发竞争、幂等重放、价格/状态复验及越权。默认用`scripts/verify-mysql-isolated.py`的新建临时库 |
| 登录、成员与角色权限、Redis保护 | 未登录、跨商户、撤权/禁用、CSRF、双实例共享状态与依赖故障；相关MySQL/Redis JUnit及`scripts/smoke-redis-shared.py` |
| API或数据库 | `verify-api-contract.py`、`verify-api-schemas.py`、`schema_contract.py --check`；真实新库/升级/重放/校验和拒绝 |
| Python/AI及外部I/O | `ai-service`的pytest、`scripts/smoke-ai-local.py`；验证权限白名单、降级、容量、超时与失败恢复。真实供应商结果单独记录 |
| 页面、前端交互 | 格式、UI生成检查；相关Chromium契约和真实后端页面检查。明确替身与真实后端的区别 |
| CI、构建与部署配置 | 工作流触发/语法、格式、UI可复现构建及对应Actions；镜像或运行拓扑改变时验收实际交付镜像 |

Java全量构建必须有隔离MySQL及所需Redis环境，不能把跳过的集成用例算作通过。Windows可运行`python scripts/verify-mysql-isolated.py --help`查看二进制/端口参数，Linux CI复用仓库Wrapper。现有运行与证据入口见 [Redis运行手册](../operations/REDIS-12-runbook.md)。

审查最终差异中的行为、兼容性、安全、事务、迁移和测试证据；规格或源码变更后修正引用文档，不继续在AGENTS.md堆积执行记录。

## 5. PR 验收

填写 [PR模板](../../.github/pull_request_template.md) 的六项，可标明“不涉及”并说明依据。提交、推送和创建PR依本次任务授权执行。正文描述最终实现，代码更新后同步结果，不用旧提交的绿色检查代替最新提交。

所有PR及main推送均触发现有验收工作流，不在工作流级别按路径跳过。门禁检查名与 [main保护配置](../../.github/rulesets/main-quality-gates.json)一致；修改名称/矩阵/条件时必须同步检查保护规则，不能遗留永远等不到的必需检查。可选外部AI不作为常规合并必需项，未执行写`NOT_RUN`。

PR模板负责说明，GitHub Actions负责机器可验证的检查，代码/业务审查负责判定实现是否符合目标。三者不互相替代。发现CI失败须读原始日志定位原因，不把失败简单归为偶发后反复重跑直到绿色。

## 6. 合并交付

确认最新PR版本、目标main及必需检查通过，检查合并前差异和未解决审查意见。个人开发可要求PR但不强制第二个人审批；AI可以审查和修复，合并仍须本次任务有明确授权，不因有权限或绿色CI自动执行。

合并后核对main提交和对应Actions。依赖PR合并后，重新核对后续PR差异及合并基线的CI。数据库升级、运行服务替换、真实模型验收、部署和分支清理分别按范围授权。

最终交付报告写清修改、实际测试结果、证据、未验证事项及仓库/运行状态：

- **代码完成**：实现已提交，尚不能推断测试或联调通过。
- **测试通过**：明确环境、范围、数量、失败/跳过及最终修复结果；替身/H2/静态检查不冒充真实后端。
- **列明范围业务验收通过**：实际业务链路在指定版本、环境与数据上执行，附证据；不扩大为生产、性能或外部AI通过。

本流程不新增真实资金行为、生产部署承诺或自动AI合并。历史证据继续保留在`docs/testing/`，新结果按任务单独记录。
