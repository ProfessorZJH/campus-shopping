## 二、答辩现场 8 分钟“黄金闭环”演示剧本与防翻车预案

### 2.1 演示前 30 分钟准备清单（防翻车铁律）
1. **准备双环境兜底**：
   - 首选：提前在本机启动 MySQL 8.0、Redis、Java 后端（`8091`）与 Python `ai-service`（`8100`），浏览器提前打开 **两个独立窗口**（普通窗口登录“学生消费者”，无痕窗口准备登录“商户店主 / 平台管理员”），避免演示中途反复退出重登浪费时间。
   - **断网/API 故障兜底**：答辩教室校园网常屏蔽外部端口或信号极差。本系统在未配置或断开外部 LLM API 时会自动平滑运行于本地混合检索模式，**提前测试一遍无外网情况下的问答流畅度**，即使教室彻底断网也能完整跑通所有演示！
   - **录屏双保险**：答辩前一天按下方 8 分钟动线录制一段无剪辑高清 MP4 放在桌面，万一现场投影分辨率异常或电脑重启，随时可切视频保底。

### 2.2 8 分钟跨三端现场演示动线（紧扣架构亮点，不演流水账注册）

1. **第 0～2 分钟 · 消费者端：AI 流式导购与“提案两阶段安全确认”**
   - 在 `/#/ai` 输入带预算与排除约束的自然问题（如：*“预算 25 元以内，帮我挑两瓶无糖茶饮，不要含糖的”*）。
   - 边演示边向评委指出两处细节：**① 流式状态与引用来源展示；② AI 只生成了带实时单价的“待确认商品卡片”，右上角购物车数字此刻仍为 `0`（证明模型无直接写权限）**。
   - 点击“确认加入购物车”，展示购物车数字实时增加。

2. **第 2～4 分钟 · 消费者端 ↔ 商户工作台：并发锁库结算、备货与动态码核销**
   - 消费者在购物车点击结算生成待支付订单，点击“模拟支付”（讲解：同事务内记账并生成门店 `WAIT_PREP` 自提任务，库存进入 `reserved` 预占态，实物 `on_hand` 尚未扣减）。
   - 切换到无痕窗口 **商户工作台（`/#/merchant/orders` & `/#/merchant/pickup`）**：点击“开始备货” → “备货完成”；切回消费者页面签发动态自提核销码，复制核销码到商户端完成核销（讲解：此时同一本地事务才真正扣减 `on_hand` 与 `reserved` 并留存库存流水 `CONSUME`）。

3. **第 4～6 分钟 · 商户自定义 RBAC 与售后争议平台裁决**
   - 展示商户工作台 `/#/merchant/roles` 15 项细粒度权限勾选与 `/#/merchant/inventory` 低可售库存预警及流水追踪。
   - 快速演示一笔未提货订单：**消费者申请退款 → 商户驳回 → 消费者申诉 → 切换平台管理员（`/#/admin/disputes`）裁决通过退款并自动释放预占库存**，体现三方权责闭环。

4. **第 6～8 分钟 · 平台知识库调试台与工程门禁收尾**
   - 打开 `/#/admin/knowledge/debug`（RAG 检索调试台），输入售后/自提规则问题，展示各分块的 RRF 分数、版本号与命中排名，直观证明检索引擎是**白盒可解释、权限受控**的，而非黑盒调包。

## 三、终期毕业答辩 12 道深水区技术追问 Q&A 速查卡

1. **问：你的 Java 后端和 Python 服务之间是怎么保证通信安全的？前端能不能绕过 Java 直接调 Python？**
   - **答**：不能。第一，网络拓扑上（见 `compose.yml`）Python `8100` 端口仅暴露在容器内网，不映射宿主机公网端口；第二，应用层强制校验长度不少于 24 位的共享密钥 `X-Service-Key`，并采用常量时间比较 `secrets.compare_digest` 防止时序攻击；第三，Python 端所有 ACL 文档白名单和商品实时报价均由 Java 查库后注入，Python 自身不信任任何外部身份声明。

2. **问：为什么你在 `ShoppingAiCaseImpl.chat` 上加了 `@Transactional(propagation = Propagation.NEVER)`？**
   - **答**：为了从架构机制上根治“长耗时外部 RPC 拖死数据库连接池”。大模型单次推理可能耗时 5～30 秒，如果方法被外层事务包裹，HikariCP 连接和 InnoDB 行锁会被长期占死。使用 `Propagation.NEVER` 后，一旦有人误在调用链上游开启事务会直接抛异常阻断；会话并发互斥改用毫秒级短事务写入 `ai_conversation` 表的 600 秒 `turn_token` 租约实现，长调用期间数据库连接占用数为 **0**。

3. **问：如果用户在 AI 流式回答生成到一半时，管理员把某篇内部知识文档撤稿了，或者店主把这个店员开除了，会发生什么？**
   - **答**：会被系统立即拦截并返回 `KNOWLEDGE_NOT_READY`，已生成的文本绝不会返回或落库。我们在调用 Python 前（第 1 次）、Python 返回后生成提案前（第 2 次）、最终短事务落库前（第 3 次），用 `REQUIRES_NEW` 独立只读事务绕过一级缓存重算用户可读文档集合的 SHA-256 快照指纹。只要三次指纹不一致，立即熔断丢弃，彻底防御 TOCTOU（检查时到使用时）时间窗越权漏洞。

4. **问：你的 Redis 为什么拆成 `redis-security` 和 `redis-cache` 两个逻辑/物理实例？**
   - **答**：因为两类数据的内存淘汰语义完全相反！会话（Session）、CSRF、登录限流与 AI 分布式准入信号量属于**安全与协调状态**，一旦在内存满时被淘汰会导致登录态丢失或限流绕过，因此 `redis-security` 启用 AOF 持久化并配置 `maxmemory-policy noeviction`；而公开商品/商户展示缓存属于**可重建只读投影**，`redis-cache` 配置 `allkeys-lru` 允许自动淘汰冷数据，且故障时 `DisplayCache` 自动降级直读 MySQL，互不干扰。

5. **问：缓存和数据库双写一致性你是怎么处理的？**
   - **答**：针对商品展示缓存，采用 **Cache-Aside + 事务提交后淘汰（`TransactionSynchronization.afterCommit`）+ 随机过期抖动 + 损坏 JSON CAS 自愈**；针对商户公开信息，更进一步采用 **数据行版本号嵌入缓存 Key（`merchant:v2:{id}:{version}`）**，先按主键极速读取 `status, version` 再命中对应版本缓存，从根源上消除了并发读写下的脏缓存窗口。

6. **问：数据库金额字段用的什么类型？为什么不用 `Double` 或 `DECIMAL`？**
   - **答**：全链路（MySQL 表字段 `BIGINT`、Java `long priceCent`、JSON DTO、Python 预算校验）统一使用**以“分”为单位的 64 位整数**。IEEE 754 浮点数（`double`/`float`）存在二进制精度丢失（如 `0.1 + 0.2 != 0.3`），而整数分运算在加减乘及总价核对时绝对精确、性能最高，仅在前端视图层格式化为 `¥xx.xx` 展示。

7. **问：如果用户在 AI 推荐出“10 元特价商品”后过了 5 分钟才点确认加购，这 5 分钟内商家把价格改成了 15 元，系统怎么处理？**
   - **答**：提案生成时在 `ai_proposal` 中快照了当时的 `priceCent=1000` 和商品聚合版本号 `quoteVersion`（源自 `cat_product.version`）。5 分钟后用户点击确认时，`ProposalConfirmationCaseImpl` 在同一数据库事务中按确定性锁序锁定当前商品与 SKU，比对 `o.priceCent() == item.priceCent() && o.version() == item.quoteVersion()`。发现版本或价格已变，立即抛出 `C0002（商品价格已变动）` 回滚事务，前端保留用户勾选状态并提示刷新最新报价，绝不按过期价格成交，也绝不悄悄按涨价后的价格强买。

8. **问：自提核销码是怎么存储和防伪造的？**
   - **答**：数据库 `ful_pickup_task` 表中**不存储明文自提码**，只存储高熵随机令牌的 **SHA-256 哈希摘要**及过期时间。买家每次重新签发自提码都会原子覆盖旧哈希使旧截图立即作废；店员核销时需同时具备当前商户的 `pickup.verify` 权限、订单无挂起退款单，且提交令牌哈希匹配，核销成功后立即清空有效状态防止二次提货。

9. **问：前端切换账号或切换所管理的商户时，如果上一个账号发出的慢请求刚返回，会不会把旧数据渲染到新账号界面上？**
   - **答**：不会。我们在前端状态层设计了五维单调递增代次令牌（`generation`、`sessionEpoch`、`merchantEpoch` 等）。每次登录/退出/401/切换商户时立即自增所有 Epoch 并清空私有状态；在 `api.js` 每次网络响应解析后、CSRF 自动重试前及 SSE 每个事件帧分发前，强制执行 `requireIdentity(stamp)` 校验代次，过期上下文的响应会被直接丢弃。

10. **问：为什么数据库升级不在 Spring Boot 启动时自动跑 Flyway DDL，而要单独写 `schema_contract.py`？**
    - **答**：在多实例部署下，应用启动自动跑升级 DDL 容易发生并发锁表、半截失败难回滚，甚至把缺表的残缺旧库误标为已升级。本系统坚持“**应用启动只读校验 `sys_schema_migration` 版本与 SHA-256 校验和，结构变更必须在维护窗口显式执行迁移脚本**”，并在迁移前计算 `information_schema` 归一化结构指纹与历史发布基线对账，未知结构漂移一律阻断并强制人工审计留痕。

11. **问：为什么几乎所有业务异常都返回 HTTP 200 配合非 `0000` 的 `code`，而入参格式错误返回 HTTP 400？**
    - **答**：这是项目在 ADR-012 中明确记录的统一契约：协议级错误（未登录 `401`、无权限/CSRF 失效 `403`、JSON 语法损坏或超限 `400/413`）由 Spring Security 与 `ApiProtocolExceptionResolver` 返回标准 HTTP 状态码；进入领域用例后的业务规则拒绝（如库存不足 `I0001`、价格已变 `C0002`）在事务代理外层回滚后由 Controller 统一封装为业务码信封，前端 `api.js` 严格同时校验 `r.ok && j.code === '0000'`。

12. **问：这套系统目前最大的扩展瓶颈在哪里？如果全校几万人同时用怎么演进？**
    - **答**：当前 Java 层已通过无状态设计 + Redis 共享会话支持水平扩容多实例；主要单点瓶颈在：① Python `ai-service` 的知识分块主存使用了本地 SQLite WAL（限制为单实例），下一步可将分块正文与向量统一迁入 Qdrant/PostgreSQL 实现多副本扩容；② 商品模糊搜索在高基数下使用 SQL `LOCATE` 扫描，下一步可引入 MySQL ngram 全文索引或专用检索引擎承接流量，仅对召回结果回主库复核实时库存。
