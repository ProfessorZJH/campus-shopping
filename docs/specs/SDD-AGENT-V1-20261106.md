# 校园商城 Agent v1.0 架构设计基线

> 状态：设计冻结候选（2026-11-06），等待文档 PR 审阅后作为实施基线。本文件不表示已开发、测试、合并或部署。
>
> 适用范围：ProfessorZJH/campus-shopping；消费者导购及商户经营 AI。依据现有 PRD、RBAC、ShoppingAI、Java DDD / Python FastAPI 架构。业务行为与现行 PRD 不一致之处参见「契约迁移」。

## 1. 产品体验与业务身份

**面向用户只有一个 AI 助手入口，不要求消费者或商户手动选择 Agent / 工作空间。**

内部保留 ConsumerAgent 和 MerchantAgent 两组业务工具与提示策略，共用同一 Python Agent Runtime。其划分是实现细节，不应要求用户理解或操作“工作空间”“Agent 类型”。

同一 userId 可同时为消费者、A 店 Owner、B 店 Clerk。一次输入可以同时包含消费者和商户任务；运行时可路由到对应的受限能力，不要求用户更换页面或开启另一条会话。**统一交互不等于统一权限**。用户的商户成员身份不是“默认当前正在操作这个商户”。

### 1.1 自动识别目标，不自动猜测不确定的商户

意图路由与业务范围解析分离：

1. **业务意图候选**：根据本轮请求和历史事实，判定购物、本人订单、商户经营、知识问答、混合任务等；模型只提出可能的能力及工具。
2. **实体绑定**：优先提取用户明确提及的店名、订单号、商品 SKU、当前任务中的唯一实体引用；由 Java 查询归属与可访问范围。
3. **可信范围判断**：Java 从认证 userId、当前有效商户成员/角色/资源归属及业务状态形成实际可访问范围。客户端页面上下文可以作为辅助线索，不是不可绕过的前置选择，也不能作为授权依据。
4. **歧义澄清**：当多个商户/订单都满足条件且没有唯一锚点时，对具有修改效果的动作必须先明确目标，禁止静默选一家店。只读可在用户要求“所有我管理的门店”时逐商户授权并返回分组汇总。
5. **执行前重新复权**：权限、商户状态和资源可能变化，发起工具调用及完成写操作时均由 Java 重新校验。

示例：
- 「给我推荐 30 元以内的牛奶」→ ConsumerAgent，公开商品检索。
- 「A 店今天多少待备货订单？」→ MerchantAgent，Java 解析 A 店并核验 order.read。
- 「我昨天买的那笔订单呢？」→ 消费者订单范围；关联当前会话唯一已验证实体，无法唯一定位则澄清。
- 「查一下我两家店的库存」→ 枚举当前用户有效授权商户，逐店查询、分别展现，无横向越权。
- 「把那件商品降价 10%」且用户管理多个商户、缺少唯一 SKU → 询问哪件商品/哪家店；不能用最近访问的店默选并写入。

## 2. 目标架构与责任

浏览器统一 AI 助手
→ Java Agent Application（可信身份、领域授权、Run、会话/Memory、任务上下文）
→ Python FastAPI + OpenAI Agents SDK（Consumer / Merchant Agent 配置、工具选择、模型交互、Tracing）
→ Java Tool Gateway（用户与 Run 的受控绑定、鉴权、参数校验、限额与幂等）
→ 原有 Java Case / Domain（Catalog、Inventory、Trading、Fulfillment、Identity、Knowledge）及 MySQL、Milvus。

SDK 是**验证后首选实现**，不是架构安全保障。需要在 NVIDIA / 讯飞等现有 Chat Completions 兼容服务上测试 Function Calling、流式工具、Usage 和异常行为；追踪导出必须先确认数据外发政策。兼容性失败可改适配层，不改变 Java 业务边界。

Java → Python → Java 调用不得跨模型调用长期持有数据库事务或业务行锁；内部 Java Tool Gateway 不得重新抢占同一轮会话租约。Python 不直接写交易数据库。

## 3. 意图理解、Tool Calling、Action Policy

- 不要求每轮先单独调用一次 Intent LLM。Context Resolver 识别追问、指代、纠正、否定、条件、任务切换；Agent 借由实际工具调用逐步完成任务。
- 模型不能凭提示词获得消费者/商户授权，也不能根据模型生成的 merchantId / userId 扩大范围。
- 工具提供面向业务的有限能力，而不是开放任意数据库查询或全部 Controller。初步候选：
  - Consumer：商品检索、SKU 详情及实时价格库存、公开/授权知识、本人订单/售后、购物车操作；
  - Merchant：当前获授权商户的订单待办、库存汇总、订单详情和商户知识；首期只读。
- 模型返回“我已加购”不构成事实。最终以 Java 提交的业务结果为准。
- 明确授权、唯一 SKU 和完整数量的低风险加购可以直接执行，仍需 Java 原子性与稳定幂等键；无明确授权的推荐不触发写操作。
- 模糊指令追问；商户改价/批量变更/退款审核等较高风险操作先预览确认；支付、权限授予等敏感操作不授权模型自主执行。
- 工具错误要可区分参数错误、资源不存在、无权、业务冲突、可重试超时。已提交结果不因 SSE 断开/模型超时而回滚；写操作重试须通过业务 actionId 查询状态，杜绝重复加购。

## 4. Memory 与上下文保真

统一对话入口，**内部记忆按任务和资源的真实授权范围隔离**：

- **History**：MySQL 保留完整原始消息；不因摘要压缩删除原文。
- **Summary**：仅做早期消息的有损语义概览，记录 coveredSeq、来源和版本。
- **Structured Facts**：无损保存订单号、SKU、数量、金额、用户否定/条件、原文 messageId、验证标记。用户提供实体先记 USER_SUPPLIED，Java 验证存在与归属才记 VERIFIED。
- **Task State**：当前目标、活动实体引用、待补参数、任务切换和操作执行状态。
- **Long-term Preferences**：仅明确、相对稳定且允许保存的偏好，可查看、修改、删除；不把一次性预算写成永久画像。

上下文装配包括当前输入、当前任务事实、最近原文、相关摘要和必要时通过授权校验回溯的历史原文。摘要与原文冲突时以原文和实际工具事实复核，无法消歧则追问。**价格、库存、订单状态、权限永远从 Java 当前业务事实获取**。

消费者私人历史不能作为商户内部知识使用；A 店的私有资料不得在 B 店相关任务中进入模型上下文；同一聊天中多业务意图需要分段装配/严格过滤工具证据。撤权、知识版本变化后对应记忆不能再被召回。

首期使用已有 ai_conversation、ai_message，按需迁移增加 agentType、结构化会话状态、带来源的偏好存储。SDK 不另建与 Java 冲突的第二套业务会话库。初期不引入向量记忆数据库、Neo4j 或独立 Memory Agent。

## 5. Run、SSE 与可观测性

Run 逻辑生命周期：CREATED → RUNNING → SUCCEEDED / FAILED / CANCELLED；按业务需要 WAITING_INPUT / WAITING_APPROVAL。conversation 与 Run 是不同概念。每个 Run 绑定可信发起者、任务/实体上下文、traceId、截止时间和调用预算。

限制模型轮次、工具次数、并发、总时长与成本。取消不等于回滚已完成写操作；工具超时要先检查幂等状态，不无限重试。

SSE 提供用户可理解的 run/tool 状态、经过校验的回答、结构化商品/订单卡片、操作结果与错误；不向用户输出模型内部推理。事件包含 runId、conversationId、sequence 供去重/断线恢复。

SDK Trace 追踪模型与工具；Java 与 Python 用 traceId 关联。默认不在第三方 Trace 平台保存完整用户问题、订单敏感字段和内部文档正文；明确脱敏、保留期限和数据外发审批。

## 6. 验收门槛

必须包含：真实模型 Tool Calling；身份路由正确；同一用户同时具有消费者与多个商户身份时自动解析；跨商户不串读；模糊修改请求不选错商户；多意图/否定/条件保真；超过 30 轮后订单号和 SKU 可回溯；历史摘要不取代实时订单状态；权限撤销即时拒绝；写操作原子幂等；网络超时/模型失败/取消后结果可信；SSE 断线不产生重复执行；Trace 不泄露敏感信息。

跨租户越权、未授权写入或重复业务动作是阻断性缺陷。Mock 全绿不等于真实 Agent 业务验收完成。

## 7. 分阶段交付

A. POC：Agents SDK 与现有第三方模型工具调用/Trace、最小 Java 只读 Tool Gateway。
B. ConsumerAgent：自动意图处理、商品/RAG/本人订单、稳定的结构化实体、低风险直接加购，保留原有业务能力。
C. Memory 与产品体验：摘要保真、Fact/Task State、原文回溯、SSE、可控成本/失败恢复。
D. MerchantAgent：多商户自动范围解析、RBAC、经营只读能力；高风险经营写动作按后续 SDD 开发。

## 8. 契约迁移与冻结规则

本文件是**目标设计**。当前 docs/requirements/PRD.md 仍规定 AI 加购必须二次确认，与新设计低风险明确授权直接加购冲突；实现前必须同步 PRD、购物 AI SDD、API、数据库迁移及验收用例，不可只删除确认按钮。

现有消费者导购是固定 Java → Python 检索/推荐流程；商户 Agent 与动态工具调用尚未实现。已有购物车/Proposal、商品索引、会话租约、RAG 权限、订单事务优先复用。

冻结原则：**统一无选择器的 AI 交互、双业务 Agent 配置、Java 可信执行边界、商户级强隔离、事实可追溯、低风险明确授权直执行、订单库存实时查询**。任何要改动上述业务语义的方案，必须重新提出影响范围、迁移和验收依据。
