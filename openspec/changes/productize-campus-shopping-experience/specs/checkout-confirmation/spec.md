# Spec Delta

## Purpose

为消费者在下单前提供可核对的商品、金额和自提信息，并在数据变化或提交失败时提供恢复路径。此能力增加确认体验，继续遵循既有单商户订单、服务端复验与幂等规则，不引入真实支付或促销计算。

## ADDED Requirements

### Requirement: 提交前展示当前确认信息

系统 SHALL 在正式提交前使用重新获取的购物车和门店信息展示商户、自提地点、商品、规格、数量、价格与合计，明确模拟支付语义。加载失败或存在不可售项目时不能将旧内容作为已核实结果提交。

#### Scenario: 用户从购物车进入确认
- **WHEN** 用户选择同一商户的商品并进入结算确认
- **THEN** 页面展示本次重新获取的信息，用户可以返回调整后再次确认

#### Scenario: 确认信息获取失败
- **WHEN** 获取当前价格、可售状态或门店信息失败
- **THEN** 系统保留用户选择并允许重试，不直接提交旧的确认内容

### Requirement: 变化与提交失败具有明确恢复路径

系统 SHALL 对价格、版本、库存或可售状态变化给出可理解的反馈，保留仍有效的用户选择，并在内容改变后要求重新确认。确认页不预留库存、不承诺锁价，也不能跳过提交时的权威复验。

#### Scenario: 确认之后价格或库存变化
- **WHEN** 用户提交时服务端检测到变价、缺货或商品下架
- **THEN** 页面显示相应原因，更新受影响内容，并允许用户调整或重新确认

#### Scenario: 同一次提交结果未知
- **WHEN** 提交因连接中断而无法立即确认结果，用户重试同一内容
- **THEN** 系统沿用既有幂等语义恢复结果，不生成重复订单或错误宣告原订单失败

### Requirement: 确认页明确区分提交中和完成

系统 SHALL 在提交期间防止重复交互，并仅在取得可识别的订单结果后进入订单详情。请求失败时保留可恢复的表单状态，不将请求结束等同于业务成功。

#### Scenario: 用户连续点击提交
- **WHEN** 同一次提交仍在处理中，用户再次触发提交动作
- **THEN** 页面明确显示处理中，结果只对应一个幂等订单

#### Scenario: 提交被业务校验拒绝
- **WHEN** 服务端返回业务拒绝结果
- **THEN** 页面停留在可调整的确认流程，显示错误并保留有效输入
